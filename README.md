# epay-gateway：统一支付网关

一个**兼容易支付（epay）协议**的轻量支付网关，使用 Go 编写，单文件部署、无需 CGO。
商户（如 [new-api](https://github.com/QuantumNous/new-api)）按易支付协议接入，网关再对接真实的支付渠道，并自带可视化管理后台。

| 支付方式标识（可自定义） | 驱动 | 支付产品 |
| --- | --- | --- |
| `alipay` | `alipay` | 电脑网站支付 / 手机网站支付 / 当面付扫码（RSA2 公钥模式） |
| `wxpay` | `wechat` | 微信支付 APIv3：Native 扫码 / H5（微信支付公钥验签） |
| `paypal` | `paypal` | PayPal Orders v2（自动汇率换算、Webhook 兜底） |
| `stripe` | `stripe` | Stripe Checkout（银行卡、Apple Pay、Google Pay 等） |
| `mock` | `mock` | 模拟支付，仅用于联调测试 |

## 特性

- **协议兼容**：`submit.php` / `mapi.php` / `api.php`（查单、退款），签名规则与彩虹易支付一致；用 new-api 实际使用的 `go-epay` 客户端做了兼容性测试。
- **可视化管理后台**：`/admin/` 下配置商户与支付渠道（即时生效、无需重启），查看成交统计与订单，一键补发通知、主动查单。
- **可靠通知**：通知队列持久化在数据库中，失败按 15s → 15s → 30s → 3m → … → 15h 重试共 12 次，进程重启不丢失。
- **双重确认**：上游异步通知 + 买家跳回 / 收银台轮询时主动查单，任一路径先到都能正确入账；重复回调严格幂等。
- **资金安全**：金额全程以「分」为整数计算；入账前核对上游实付金额与币种；退款先原子占用额度再请求上游，防止超额退款。
- **易扩展**：新增渠道只需实现一个接口并声明配置字段，后台表单自动生成，无需改动已有代码。

## 快速开始

```bash
git clone git@github.com:Alndaly/epay.git && cd epay
cp config.example.yaml config.yaml              # 把 server.base_url 改成你的公网域名
echo "ADMIN_PASSWORD=$(openssl rand -hex 8)" > .env
docker compose up -d
cat .env                                        # 管理后台密码
```

打开 `https://你的域名/admin/`（账号 `admin`）：

1. **支付渠道 → 新建渠道**：接入支付宝 / 微信 / PayPal / Stripe，参数获取方式见[渠道申请与配置](docs/channels.md)。
2. **商户 → 新建商户**：得到支付地址、商户 ID、商户密钥。
3. 把这三项填进 new-api，详见[接入 new-api](docs/new-api.md)。

不用 Docker 时，`make build`（需要 Go 1.25+ 与 pnpm）会构建前端并编译出 `bin/epay`。

> 想先跑通全流程？新建一个「模拟支付」渠道，收银台会出现「模拟支付成功」按钮，可走完回调 → 入账 → 通知商户的完整链路，验证后请删除。

## 架构

```
            易支付协议                                上游渠道协议
 商户 ───────────────────▶ ┌──────────────────────┐ ───────────────▶ 支付宝 / 微信 / PayPal / Stripe
(new-api) ◀── 异步通知 ─── │  server   HTTP 协议适配 │ ◀── 异步通知 ────
                           ├──────────────────────┤
                           │  gateway  核心业务    │  下单·确认支付·通知重试·查单·退款·配置热更新
                           ├───────────┬──────────┤
                           │  provider │  store   │  渠道抽象 / 订单与配置存储（均为接口）
                           └───────────┴──────────┘
                                    ▲
                           admin + web  可视化管理后台
```

**一笔订单的生命周期**

1. 商户提交 `submit.php` → 网关验签、落库，调用渠道下单；
2. 跳转类渠道（支付宝网页、PayPal、Stripe）直接 302 到上游；扫码类（微信 Native、当面付）进入网关收银台展示二维码；
3. 买家付款后，上游回调 `/notify/{type}`（或买家跳回时网关主动查单）→ 核对金额 → 订单置为已支付；
4. 网关以 GET 请求商户 `notify_url`（带签名的标准易支付参数），商户返回 `success` 即完成；
5. 买家被带着同样的签名参数跳回商户 `return_url`。

目录结构与各层职责见[开发指南](docs/development.md)。

## 注意事项

- 网关必须通过**公网 HTTPS 地址**访问，否则上游渠道无法回调。
- `mock` 渠道任何人都能触发支付成功，**生产环境务必删除**（启动时会打印警告）。
- 支付宝目前只支持「公钥」加签模式，不支持公钥证书模式；外币渠道不支持 JPY、KRW 等无小数位币种。
- SQLite 以单连接 + WAL 模式运行，适合单实例部署；多实例需按 `store.Store` 接口实现 MySQL / PostgreSQL 存储。
- 退款接口对上游请求失败时会回滚本地额度，但若上游实际已退款而响应丢失，需要到渠道后台核对。
